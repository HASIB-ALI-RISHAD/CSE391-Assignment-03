CREATE TABLE IF NOT EXISTS users (
    user_id INT NOT NULL AUTO_INCREMENT,
    username VARCHAR(60) NOT NULL UNIQUE,
    full_name VARCHAR(100) NOT NULL,
    phone VARCHAR(20) NOT NULL,
    address VARCHAR(255) NOT NULL,
    password VARCHAR(255) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (user_id)
);
 Client Accounts Table (users)
  • CREATE TABLE IF NOT EXISTS: Prevents errors if the table was already created on a prior run (idempotent DDL).
  • user_id INT NOT NULL AUTO_INCREMENT: Surrogate primary key. MySQL automatically assigns 1, 2, 3... to each new user.
  • username VARCHAR(60) NOT NULL UNIQUE: The UNIQUE constraint guarantees that no two clients can register with the exact same username.
  • full_name, phone, address: Stores the client's profile details. When a client signs in, these are pulled into $_SESSION and auto-populate their booking form.
  • password VARCHAR(255) NOT NULL: Stores the client's login password. Allocated 255 chars to accommodate secure hashes.
  • created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP: Automatically logs the date and time when the account was registered.
  • PRIMARY KEY (user_id): Declares user_id as the unique identifier and automatically creates a clustered B-tree index.

CREATE TABLE IF NOT EXISTS appointments (
    appointment_id INT NOT NULL AUTO_INCREMENT,
    user_id INT NULL,
    client_name VARCHAR(100) NOT NULL,
    address VARCHAR(255) NOT NULL,
    phone VARCHAR(20) NOT NULL,
    car_license VARCHAR(50) NOT NULL,
    car_engine VARCHAR(50) NOT NULL,
    appointment_date DATE NOT NULL,
    mechanic_id INT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (appointment_id),
    FOREIGN KEY (mechanic_id) REFERENCES mechanics(mechanic_id)
);
 Appointments Table (appointments)
  • appointment_id: Unique booking ID (1, 2, 3...).
  • user_id INT NULL: Foreign reference back to users.user_id. Can be NULL for initial demo seed rows or guest records, but holds the client ID for logged-in bookings.
  • client_name, address, phone: Snapshot of the customer's contact info at the moment of booking.
  • car_license: Registration plate number (e.g., 'DHAKA METRO-GA-12-3456').
  • car_engine: Engine number (checked for digits only).
  • appointment_date DATE NOT NULL: The service date stored in ISO standard format (YYYY-MM-DD).
  • mechanic_id INT NOT NULL: Identifies the chosen mechanic.
  • FOREIGN KEY (mechanic_id) REFERENCES mechanics(mechanic_id): Relational constraint. Prevents creating a booking for a mechanic ID that does not exist in the mechanics table.
💡 Likely Viva Questions for database.sql
Q1 Why did you use FOREIGN KEY on mechanic_id?
To guarantee referential integrity. A foreign key ensures that an appointment cannot be booked for a mechanic that doesn't exist in the database, and prevents deleting a mechanic while appointments are still linked to them.
Q2 Why did you separate mechanics and appointments into two tables instead of one?
This follows Database Normalization (up to 3NF). If mechanic name, specialty, and phone were stored directly inside the appointments table, mechanic info would be repeated redundantly for every car, causing update anomalies and data duplication.
Q3 What data type did you use for appointment_date and why?
The DATE data type (format YYYY-MM-DD). It uses only 3 bytes of storage and allows native date comparisons (e.g. appointment_date >= CURDATE()) and proper chronological sorting without string parsing.

function is_valid_date($date) {
    if (!preg_match("/^(\d{4})-(\d{2})-(\d{2})$/", $date, $parts)) {
        return false;
    }
    return checkdate((int)$parts[2], (int)$parts[3], (int)$parts[1]);
}
 Date Validation Helper (is_valid_date())

  • checkdate($month, $day, $year): Built-in PHP function that verifies the date is a legitimate Gregorian calendar date (e.g., rejects impossible dates like February 30 or April 31).

💡 Likely Viva Questions for db.php
Q1 How does db.php know whether it is running on XAMPP or the internet?
By inspecting the superglobal variable $_SERVER['SERVER_NAME']. If it equals 'localhost' or '127.0.0.1', it loads the local root credentials and creates cse391_workshop. Otherwise, it uses the remote host and database credentials for InfinityFree.
Q2 Why do you use mysqli instead of the older mysql_connect()?
The old mysql_* functions were deprecated in PHP 5.5 and completely removed in PHP 7.0. mysqli is the modern, secure, object-oriented MySQL extension supporting prepared statements, UTF-8 character sets, and improved performance as taught in Lecture 06.
Q3 What is the purpose of the h() function?
It is a shorthand wrapper for htmlspecialchars(). It prevents Cross-Site Scripting (XSS) attacks by converting HTML characters into entities before rendering them into the browser.

💡 Likely Viva Questions for login.php
Q1 How does single sign-in work when there is both an admin and multiple clients?
When the form is submitted, the script first checks if the input matches the constant admin credentials (ADMIN_USERNAME and ADMIN_PASSWORD). If so, it sets $_SESSION['user_role'] = 'admin' and redirects to admin.php. Otherwise, it searches the users database table; if a client match is found, it sets $_SESSION['user_role'] = 'client' and routes to index.php.
Q2 Why did you use $db->real_escape_string() on the username and password?
To defend against SQL Injection. If an attacker enters admin' OR '1'='1, without escaping, the single quote breaks out of the SQL string and compromises the database. real_escape_string() prefixes special characters with backslashes to ensure input is treated strictly as literal data.

Q3 What does event.preventDefault() do?

1. Relational Database & Normalization

  • 1NF: Atomic columns, no repeating groups.
  • 2NF: No partial dependency on primary keys.
  • 3NF: No transitive dependency. Mechanic details (specialty, phone, capacity) are stored in mechanics, not duplicated in appointments.
  • Foreign Key: FOREIGN KEY (mechanic_id) REFERENCES mechanics(mechanic_id) ensures referential integrity.

2. Web Security: SQLi & XSS

  • SQL Injection: When untrusted user input alters the SQL query structure. Defended using $db->real_escape_string().
  • Cross-Site Scripting (XSS): When malicious JavaScript is injected into web pages viewed by other users. Defended using htmlspecialchars() via our helper function h().

3. Sessions vs Cookies

  • Session: Stores sensitive user state (such as user_id and user_role) securely on the server.
  • Cookie: A small token (PHPSESSID) stored on the browser to link the client to their server-side session.
  • Lifecycle: session_start() opens/resumes, session_unset() clears variables, and session_destroy() deletes the session record.

4. HTTP GET vs POST

  • POST: Used for state-changing operations (booking, updating, deleting, login, signup). Data is sent in the request body, not exposed in the browser URL.
  • GET: Used for idempotent retrieval and bookmarkable filters (e.g., date filtering on admin.php?filter_date=2026-11-10).

5. Enforcement of Core Business Rules

  • Rule 1 (Max 4 Cars / Mechanic / Day): Checked in JS by disabling dropdown options when booked ≥ 4; enforced in PHP via SELECT COUNT(*) before insertion.
  • Rule 2 (1 Booking / Client / Day): Enforced in PHP by querying for existing appointments on that date matching user_id, phone, or car_license.
  • Rule 3 (No Past Bookings): Checked in JS by comparing against new Date(); checked in PHP by comparing $appointment_date < $today.

6. Single Sign-In Architecture

  • No separate admin sign-in page: Specification requires one unified login portal.
  • Checks for admin constants (ADMIN_USERNAME, ADMIN_PASSWORD) first → routes to admin.php.
  • Searches users table for registered clients → routes to index.php.
